# Wave 0D Implementation Plan

> Use superpowers:executing-plans inline, then one fresh whole-scope review.

Goal: reproducible Ubuntu24.04 production deployment, strict HTTPS, persistent PostgreSQL,
safe upgrade/rollback and tested backup/restore with Russian operator documentation.
Spec: docs/tasks/wave0-d-deployment.md; docs/spec/storage-control-plane-v0.1.md.
Baseline: 59d102bac0f1bf0db08b4e12bdc94e89cb402db8.

Architecture: separate production Compose over the existing Python3.13 and Web images;
Nginx terminates TLS and proxies API. Migration completes before API/worker start. Stable
bind directories preserve PostgreSQL/diagnostics across release images. Production identity,
cert/key/CA/auth files and credentials supplied outside Git. Never mount production shares.

## Rulings

- User explicitly authorized execution and main publication of the supplied written spec/plan.
  Continue inline without another design approval. Native execution already selected.
- GitNexus storage-console index absent; use source/contracts, do not touch other indexes.
- Production hostname/certificate supplied out-of-band. Public tests use synthetic certificates
  and example.test identities, isolated ports/state and a disposable DB; real values stay private.
- Until full AD/LDAP sessions/roles are implemented, the deployment gateway requires an
  operator-provided Basic-auth file for Web/read routes. This is documented break-glass access,
  not a claim that product session/RBAC requirements are implemented. Collector ingest retains
  independent bearer auth. Health/readiness exposes only generic process state.
- Dockerfiles retain development behavior; production Web is a separate build target.
- Deployments serialize via flock. No automatic downgrade or DB restore: rollback only uses
  compatible older code, otherwise explicit verified backup/restore maintenance procedure.
